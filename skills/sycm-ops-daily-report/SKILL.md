# 生意参谋 · 店铺运营日报

把「登录态复用 → 实抓多周期数据 → 口径对齐 → 出日报（含变化归因）」整条链路固化。
**输出必须全部来自实抓，一个数字都不许编。** 抓不到就写"未取到"，不要用估算值填空。

## ⛔⛔⛔ 总纲：本技能的第一性原理（先读这条，它高于本技能其余全部内容）

### ⓪ 报表的唯一目标：发现变化 → **引导找到原因**（最重要的一条）

> **实战经验（2026-09-20）**：**「你发现了数据变化，那么引导运营找到变化的原因，
> 这是很重要的事情，不然单纯的报表意义不大。」**

> **单纯的报表意义不大。** 一份好日报不是"数据陈列"，而是**一条闭环**：

```
发现数据变化 → 描述变化的数据形状 → 引导运营去查对应方向 → 运营确认事实 → 动作
      ↑                                                                    │
      └───────────────────── 下期日报验证是否闭合 ←───────────────────────┘
```

**唯一自检标准**：运营拿到日报后，**知道下一步该去问谁、查什么**吗？
如果运营看完只能说"哦，知道了" —— **这份日报就是失败的**，不管它的图表做得多漂亮。

**三条硬规定**：

1. **每一条变化，都必须配一条引导。** 不许只列数字不给方向。
2. **引导必须具体可执行。**
   「去券后台查上周券的生效区间有没有断裂」✅ ／ 「关注转化情况」❌
3. **引导的形态是"问题"，不是"断言"。**
   「上周是否调整过价格 / 优惠券？」✅ ／ 「券缩水导致转化下降」❌（后者是未经验证的结论）

> **分工**：**AI 做前半段（发现变化 + 生成引导），人做后半段（确认事实 + 执行动作）。**
> **引导的具体做法见 §4.9「店铺级：数据形状 → 引导」。**

**⓪ 是目的，①~⑥ 是实现它的纪律。** 违反其中任何一条，日报的价值归零甚至为负。

### ① 突变必有因 —— 数据不会自己变坏

> **实战经验**：**「所以任何突然的变化，肯定有原因，不可能凭空出现问题。」**
> **「所以看到这种问题就需要去考虑是否竞品竞店有调整或者自身价格优惠有调整？」**

看到突变（转化掉、流量涨、ROI 崩），**第一动作是找"谁动过什么"**，而不是**给现象起名字**：

```
自己（价格 / 券 / SKU / 主图 / 详情 / 包邮门槛 / 库存）
平台（规则 / 流量分配 / 活动排期 / 工具下线）
竞店（券后价 / 赠品 / 运费 / 主图 / 报名活动）
环境（节令 / 假期 / 物流停运 / 行业大盘）
```

### ② ⛔ 给现象命名 ≠ 找到原因

> **实战经验**：**「如果不清楚就让运营去想想他干啥了！或者让他去看竞品干啥了！别自己瞎猜」**

「流量质量下降」「承接能力不足」「跳失率变差」「人群不精准」——
这些是**现象的描述**，**不是归因**。**把它们当原因写进日报，是本技能历史上最大的错误。**

> ⛔ **反面教材（2026-09-20 某工业品店 实测）**：转化 −47.80%，日报给的归因是"承接质量恶化"
> （跳失率↑、人均浏览↓）→ 药方"改详情、加客服"。
> **真相是优惠券从 9 折缩到 92 折（09-12 起）、不再比同品牌专卖店便宜** → 买家进店比价后离开。
> **跳失率↑ / 人均浏览↓ 是"比价失败"的形状，与"承接差"形状相同、药方相反。药方完全开反。**

### ③ 能查的用数据查实，查不到的列清单交运营 —— 绝不自己编

- **数据能查**：券力度/生效日（`qn.taobao.com` 券后台，见 §2.12）、活动报名、SKU 上下架、
  价格、退款原因 → **去查**。
- **数据查不到**：运营自己动过什么、竞店改了什么、线下/工厂端 →
  **列成「需人工确认清单」**（见 §4 第 16 条）。
- **"瞎猜"的定义**：用**现象描述**冒充**归因**，且**没有验证路径**。

### ④ 转化类异常的第一问永远是：「我们自己上周动过什么？」

价格 / 券 / SKU / 主图 / 详情 / 包邮门槛 / 库存 —— **先排除自身变更，再谈外部。**

### ⑤ 🔴🔴 「运营自己犯的错」必须列为高优先假设

> **实战经验**：**「还有一个就是无法排除运营自己犯的错，比如优惠券到期忘记续期了，
> 双11等活动结束后忘记重启优惠券了」**

人为失误**不报错、不留痕、看起来像"自然下滑"**，因而最常被误当成"经营问题"去优化。
**已实测的两类**：

- **优惠券到期忘记续期** → 出现**无券空窗**。
  **识别指纹：把券按可用时间排一遍，看有没有断档。**
  （某工业品店 实测：**08-24~08-31 完全无券 8 天**、**09-01~09-11 只剩最低档 1 张券 11 天**。）
- **大促/活动结束后忘记重启优惠券** → **活动期配的券是独立批次，活动一停就失效**，极易漏重启。

→ **所有店每次复看固定两问**：**"上周券到期了没续上吗？"**、**"上次活动的券重启了吗？"**

### ⑥ 🔴🔴 认清 AI 的职责边界（实战补充）

> **实战经验**：**「还记得某母婴店有2个单品转化率下降么？最后发现是断色了！所以很多因素还是需要你发现数据变动，
> 提醒运营去查看！毕竟关联转化的因素太多了！」**
> **「你最多列出可能的因素，价格、尺码、库存、图片、优惠、差评、活动前期等等因素，
> 提出来让他去看，你只是AI，还没有碰到那么多问题，需要去积累」**

| 谁 | 干什么 |
|---|---|
| **AI** | ① **发现数据变动** ② **提醒运营去查看** ③ **给出"该查哪些方向"的清单** |
| **运营 / 店主** | ① 确认事实（上周动过什么）② 去竞店看 ③ 执行动作 |

→ **某母婴店 真实先例：2 个单品转化率下降，最后发现是「断色」** ——
  **断色不在推广数据里、也不在跳失率里**，只能靠运营确认。
→ **所以看到转化异常，正确产出是"生成排查清单发给运营"，不是"在报告里写一个原因"。**
→ **判定标准：日报里出现现象名称却没有验证路径 = 越界 + 瞎猜，必须改成清单条目。**
→ **候选因素清单见 §4.8 因素库；本次该问什么见 §4.9 形状→引导表。**

## 定位与边界（再读这条，然后往下）

> **本技能=店铺维度。** 分析单位是**「店铺整体 / 渠道 / 推广计划」**，不是单品。
> 越界做单品纵深，既拿不到够用的数据（单品级分时/地域本就没有），也会与单品技能打架。

| 维度 | 本日报做不做 | 做到什么程度 |
|---|---|---|
| **店铺整体**（GMV / 访客 / 转化 / 客单 / 退款） | ✅ **主战场** | 多周期口径 + 环比 + 归因 |
| **渠道 / 流量结构**（免费 vs 付费 / 搜索 vs 推荐 / 二级来源） | ✅ 做 | 结构占比 + 变化方向 |
| **推广计划**（分场景花费 / 点击 / ROI） | ✅ 做 | 计划级汇总 + 占比；**不逐词拆解** |
| **区域 / 时段**（店铺级 / 计划级） | ✅ 做 | 省份判据 + 时段分布（含天花板声明） |
| **单品行** | ⚠️ **只到排行榜** | Top10 的金额/环比/退款 + **一句话结构判断** |
| **单品纵深**（渠道×词、搜索vs推荐、废词、词级出价） | ❌ **不做** | → 转 `taobao-item-channel-diagnosis` |

**两条边界铁律**：

1. **单品在日报里最多是"一行"** —— 它的作用是让读者看到**店铺结构**（集中在哪几个品、谁在往下掉），
   不是让你去诊断这个品。**看到单品行有问题，正确动作是在报告里写"建议对该品单独跑单品诊断"，
   而不是在本日报里展开分析。**
2. **推广数据只到计划级汇总** —— 词级、单元级、创意级的拆解属单品/计划诊断范畴。
   日报里出现词表＝越界（且会让报告臃肿到没人读）。

> **★ 为什么这条边界要写死在技能里**：日报是**每天都要出的**，
> 一旦它开始做单品纵深，就会变成一个"永远跑不完、每天重做一遍单品分析"的怪物，
> 而真正的店铺异常（结构变化、渠道迁移、节奏错位）反而被埋掉。**分工是为了让日报能每天出。**

## 1. 口径规范（本技能最重要的一节）

铁律：**不许拿单日样本下结论，比值必须能自洽校验。**

| 口径 | 定义 | 用途 |
|---|---|---|
| **昨日** | 抓取日 −1 的**全天**（不是"实时"） | 日报抬头 KPI |
| **周对比** | 上一个**完整自然周**（周一~周日）vs 上一周期 | 看大盘涨跌 + 环比 |
| **近 7 天（滚动）** | 最近 7 个完整日 vs 前 7 日 | **看趋势是否已转向**（比自然周更灵敏） |
| **月度进度** | 本月（或活动期）起算至今累计 ÷ 目标 | 冲刺判断 |

四条硬规则：
1. **口径必须写进报告**（日期区间 + 是"全店"还是"单品" + 是否日均）。页面各模块口径常不一致。
2. **不能跨行加总**：二级来源表的子项之和会大于汇总行；**支付金额、买家数绝不能相加**。
3. **滚动 7 天 vs 自然周必须同时给**。周口径跌、滚动 7 天转正 = 下滑集中在上周前段、近期已回升 —— 这是日报里最有价值的判断，只给一个口径就会误判。
4. **"7 天 vs 30 天"不是两个独立样本**（v1.1 新增，见下节）。这是最容易犯、后果最隐蔽的口径错。

### 🔴 v1.1 核心修正：「7 天 vs 30 天」不是趋势对比

**错法**（极常见，且看起来完全合理）：
> ❌ "近 7 天转化 14.84%，近 30 天 12.30% → **变好了！**"

**为什么错**：**30 天窗口包含这 7 天**，两者共享约 23% 的数据。差异被共同部分稀释，
**方向可能完全是假的** —— 真实情况可能是 7 天在跌、30 天在涨，只是重叠段把两者拉平了。

**三种正确对比**（做趋势只能从这三个里选）：

| 方式 | 算法 | 用途 | 灵敏/稳 |
|---|---|---|---|
| **周环比 w/w** | 近 7 天 vs **前 7 天** | 短期动量、日报主力 | 最灵敏 |
| **月环比 m/m** | 近 30 天 vs **前 30 天** | 中期趋势 | 去噪 |
| **偏离基线** | 近 7 天日均 vs **前 23 天日均** | 剔除重叠后的"这周偏离了多少" | 均衡 |

**两条铁律**：
1. **总量指标必须日均化**（访客/展现/成交 ÷ 天数）才能跨窗口比。7 天总量和 30 天总量放一起比毫无意义。
2. **比率指标可直接比，但必须确认分母是哪个渠道** —— 混合口径的比率会被结构差异污染
   （典型：被灌泛流量的品，整体加购率被稀释，必须拆渠道看）。

> **⚠️ 生意参谋官方口径声明（访客分析页原文）**：
> "注意：由于部分指标 7 天、30 天统计的是**日均值**，所以会出现 7 天、30 天数据小于单日数据的情况。"
> → **官方确认 7/30 天是日均值**。做跨窗口对比时**必须日均化**，否则一上手就是错的口径。

> **万相台的「周期对比 = 周环比」正是上述标准做法** —— 直接用它给出的对比期（见 §2.7），
> **不要自己拍一个 7 vs 30**。

### 🔴🔴 v1.3 核心修正：万相台周环比有「归因成熟度」陷阱（2026-09-20 实测）

**上面那条"用万相台自带周环比"是对的方向，但有个隐藏前提没写 —— 两个窗口的归因成熟度必须一致。**

万相台是 **15 天累计归因 + 末次点击**：**近期的行还在持续回补，远期的行已经长满**。
→ **"近 7 天 vs 前 7 天"天然对近期不利**，会凭空造出一个"下降"。

**2026-09-20 某工业品店 实测（教训级）**：

| 项 | 值 |
|---|---|
| 页面给出的点击转化率环比 | **−47.80%**（1.78% vs 3.41%），看着是崩塌 |
| 但后 7 天中 **成交显示 0.00** 的日子 | **09-17 / 09-19**，合计 **481 点击 = 全窗口的 31.7%** |
| → 这 481 个点击**分母全算、分子全缺** | 转化率被**机械性压低** |
| 剔除两个未回补日 | 27 笔 ÷ 1,037 点击 = **2.60%**（**−23.7%**，不是 −47.80%）|
| 成交**日均化** | 2,561/天 vs 2,457/天 = **+4.2%（并非下降！）** |

**结论：那个"转化崩 −47.80%"的主体是口径artifact，不是经营崩塌。**
（真正的下滑幅度要靠"剔除未回补日"或"等窗口长满"才能测准。）

**三条强制规则（写进日报，缺一不可）**：
1. **凡引用万相台周环比，必须同时写出**：「本窗口内有 **N 天成交显示 0.00**（**M 点击，占 X%**）」，
   并给出**剔除后**的值。**写不出来就不许下"下降"结论。**
2. **成交/转化类总量指标必须日均化**再跨窗口比 —— 与 §1 的"7 vs 30 天"是同一条铁律的延伸。
3. **未回补日不得进入任何"崩/跌/衰退"的标题或一句话结论**；
   只能在"拐点预警"里出现，并**写明复核日**（窗口满 15 天后再看）。

> **同族错误清单**（都是"两个窗口不可直接相减"，一犯就反向）：
> ① 7 天 vs 30 天（**重叠 23%**）→ 用周环比；
> ② 万相台近 7 天 vs 前 7 天（**归因成熟度不同**）→ 剔除未回补日或日均化；
> ③ 生意参谋「周」vs 万相台「周环比」（**差一天**）→ 不可相减；
> ④ 大促前 vs 大促后（**需求被提前透支**）→ 必须同比，环比必出假"暴跌"。

### 🔴 口径陷阱：点「月」不一定落在当月（2026-09-18 实测）

**月中抓数时点首页的「月」，页面可能落在「上一个完整自然月」，不是本月进度。**
2026-09-18 抓取时点「月」，`RANGE=统计时间 2026-08-01 ~ 2026-08-31` —— 是 **8 月整月**。

- **处置**：一律先读 `RANGE=` 行确认区间，再决定怎么表述。落到上月就**如实写"8 月整月"**，绝不当"9 月进度"用。
- **月度进度另取**：真正想要的「本月进度」在页面「**店铺概况**」区块（形如 `x.xx万/xx.xx万`），单独抓。
- **别外推**：整月 GMV ≠ 滚动月窗口进度（同一时期的整月 GMV 与滚动月窗口进度，数值可差一倍以上），两个窗口不是一回事，不可互相换算。

**颜色**：后台惯例 **红＝升、绿＝降**（`--up:#d93025` 红 / `--down:#1a7f37` 绿）。
但「跳失率↑、退款率↑、退款金额↑」属于**变差**方向，涉及这类指标**必须加文字标注**（如 `（升＝变差）`），否则读者会看反。

**建议新增追踪「净支付率」** = 净支付金额 ÷ 支付金额（首页这两个值直接相除，零额外抓取成本）。
它把退款侵蚀压缩成一个 0~100% 的比例，比单看「退款率」更能回答"每卖 100 块实际到手多少"。
**判读方法**：把同店多周的净支付率拉成 **12 周序列**，看有没有**台阶式跃升** —— 跃升的那一周通常就是"换运营 / 换策略"的真实拐点。
（典型形态：低位时仅 60% 上下、退款吃掉近四成；调整后稳定在 85%~90% 区间。以上为示意数量级。）
**判定"换运营 / 换策略是否真的变好"时优先用它**——它同时吃掉转化率、客单价与退款率三者，方向比 GMV 稳、视野比转化率全。

### 🔴 致命细节：百分比的正负号不在文本里

首页数据概览每个指标的百分比**在纯文本抓取时只有数字，没有加减号**——
`12,345.00 / 5.53% / 较去年同期 / 13.19%` 读起来像 `+5.53%`，实际它是 **`−5.53%`**。

方向藏在 **CSS class** 里：

```html
<div class="index-value multiple-index-value">
  <span><span class="value undefined">12,345.</span><span class="smallValue">00</span></span>
  <span class="value down cyclecrc">5.53%</span>   <!-- down = 下降 → −5.53% -->
</div>
```

另一条同样致命的：**同一张卡片上并列着两个百分比**，靠 class 区分用途：

| class | 含义 | 说明 |
|---|---|---|
| `cyclecrc` | **环比**（较上一周期） | 日报要用的就是它 |
| `syncCrc` | 同比（较去年同期） | 文本标签会写「较去年同期」，**别拿它当环比** |

**所以：绝不可以用整页 innerText 直接读百分比方向。必须走下面的「结构化取数」。**

## 2.5 结构化取数（首页指标必须用这个）

把这段 JS 作为 `bsk_grab.sh` 的第 6 个参数传入，即可拿到「指标名 | 值 | 方向 环比」的干净结果：

```js
(function(){
  var st='';var dv=document.querySelectorAll('div');
  for(var j=0;j<dv.length;j++){var tt=(dv[j].textContent||'').trim();
    if(tt.indexOf('统计时间')===0&&tt.length<45){st=tt;break;}}
  var out=['RANGE='+st];
  var crcs=document.querySelectorAll('.cyclecrc');
  for(var i=0;i<crcs.length;i++){
    var crc=crcs[i];var card=crc;
    for(var d=0;d<6&&card.parentElement;d++){card=card.parentElement;if(card.querySelector('.index-name'))break;}
    var nm=card.querySelector('.index-name .text');
    var name=nm?(nm.textContent||'').trim():'?';
    var iv=card.querySelector('.index-value');var val='';
    if(iv){var kids=iv.children;for(var k=0;k<kids.length;k++){var ch=kids[k];
      if(ch.classList&&ch.classList.contains('cyclecrc'))continue;val+=(ch.textContent||'');}}
    val=val.replace(/\s+/g,'');
    var ct=(crc.textContent||'').replace(/\s+/g,'').trim();
    var cl=''+crc.className;
    var dir=cl.indexOf('down')>-1?'DOWN':(cl.indexOf('up')>-1?'UP':'-');
    out.push(name+' | '+val+' | '+dir+' '+ct);
  }
  return out.join('\n')||'NF';
})()
```

输出形如：
```
RANGE=统计时间 2026-09-07 ~ 2026-09-13实 时日周月自定义全部指标
支付金额 | 12,345.00 | DOWN 5.53%      ← 即 −5.53%
访客数 | 3,140 | UP 17.88%             ← 即 +17.88%
（以上数值为示意，重点看**格式与方向**，不是具体数）
```

**注意**：`[id^=top-left-overview]` 这种选择器只能命中第一张卡片（各卡片容器 id 前缀不同），
**必须像上面这样从 `.cyclecrc` 反查卡片**，才能拿到全部指标。

**拿到后必做自洽反算**（这一步能同时验证方向和数据可信度）：
用环比倒推上一周期的绝对值，再互相验算。例如 `访客 3,140（+17.88%）→ 上一周期约 2,664`；
`买家 120（−15.56%）→ 约 142`；`142/2664 ≈ 5.33%` 应≈ 上一周期转化率。对得上才敢写进报告。

## 2.6 历史周翻页抓取（做趋势 / 拐点对比必用）

日报看的是"最近一周"，**但真正能证明"运营策略变了"的是多周序列**。首页和商品排行页的「周」口径下，
日期控件右侧有一对箭头，**点「周」后左箭头启用，可以一周一周往回翻**（右箭头回最近周）。

```js
// 往前翻一周
(function(){var bs=document.querySelectorAll('button.arrow');for(var i=0;i<bs.length;i++){var ic=bs[i].querySelector('i');if(ic&&(''+ic.className).indexOf('angle-left')>-1&&!bs[i].disabled){bs[i].click();return 'L';}}return 'nf';})()
// 往后翻一周：把 angle-left 换成 angle-right
```

要点：
- `button.arrow` 在页面上有**两对**（不同模块各一组），取**第一个**匹配 `angle-left`/`angle-right` 且 `!disabled` 的即可。
- **点一次 = 一个自然周**，每次点完 `sleep 1.5~2`；停稳后要 `sleep 9~12` 再抓，否则可能拿到上一周的值。
- 用 `RANGE=统计时间 YYYY-MM-DD ~ YYYY-MM-DD` 确认当前落在哪一周（翻页进度可打印出来核对）。
- **一次命令内跑完全部翻页 + 抓取**（session 跨命令失效）；翻 11 次 + 抓 12 个点约 3 分钟，`timeout` 给 420000ms 以上。
- 抓 12 周序列的写法：先翻到最远那一周，然后循环 `抓一次 → 点右箭头 → sleep 9`。
- **商品排行页（`cc/item_rank`）同样支持**：点「周」→ 箭头启用 → 可翻历史周；列为「支付金额 / 成功退款金额 / 支付件数 / 商品加购件数 / 商品访客数」，是判断**"换品"**的硬证据。

⚠️ **翻页时不会刷新的字段**：首页「总推广花费 / 点击量 / 总ROI」在逐周翻页时**恒定不变**（属独立日期控件的残留值 —— 实测连续翻 12 周，这几个数**一点都不变**）。
**必须只用分场景花费**——`关键词推广花费 / 精准人群推广花费 / 全站推广花费 / 淘宝客佣金`，这几个才真实跟周刷新。

**用途与判读**：定位"策略拐点"（哪一周开始换打法）、验证"换人 / 改打法"的判断、对比换挡前后的效率。
判读方法：看**三条线是否在同一周同时转向** ——
① 分场景推广花费的结构变化　② 访客与转化率的**反向**跳变　③ 商品榜主推品是否换位 / 高退款品是否退场。
三条线同周转向 ≈ 人为策略调整；只有一条动，多半是正常波动，别下结论。

## 2.7 ★ 万相台「报表」= 逐日 / 区域 / 词级 数据的主力（v1.1 实测打通）

**这是 v1.1 最重要的取数发现。** 要做日报里的"逐日趋势 + 拐点"和"区域表现"，
**生意参谋根本给不了，得去万相台**：

| 想拿什么 | 生意参谋 | 万相台报表 |
|---|---|---|
| **账户 / 计划级**逐日曲线 ⭐ | ⚠️ 首页「周」不滚动 | ✅ **分天粒度**（**日报主用**） |
| 单品逐日曲线（可选） | ❌ **无接口**（单品诊断只有 7天/30天 快照） | ✅ 可得，但**日报不做单品纵深**（见「定位与边界」） |
| **周环比**对比期 | ⚠️ 首页「周」要等本周走完才滚动 | ✅ 平台算好 |
| **区域（省份）明细** | ⚠️ 仅**店铺级**（访客分析） | ✅ **计划级 / 账户级** |

### 🔴 万相台最大的口径坑：同一个「7 天成交」有两个数（2026-09-20 实测）

> **「报表」页和「计划详情」页的成交金额/笔数不是同一口径，差 19~21%。抓错源必翻车。**

| 来源 | URL 特征 | 本期 7 天成交 | 笔数 | 点击转化率 |
|---|---|---|---|---|
| 计划详情（**权威，用这个**） | `#!/manage/onesite-detail?...&effectEqual=15&unifyType=last_click_by_effect_time` | **11,324.13** | 281 | 7.29% |
| 报表页（**默认口径，别用**） | `#!/report/campaign?rptType=campaign` | 9,477.87 | 229 | 5.94% |

两个数**各自内部自洽**（229÷3,855=5.94%；281÷3,855=7.29%），所以**看不出哪个错**——
唯一判定方法是「**分日加总 = 合计**」：只有 15 天归因那条链能对上（见下）。

**强制三步**：
1. **一律以「计划详情」页为成交口径的真源**——它的 URL 显式带 `effectEqual=15`，即「15 天累计归因」；
2. **抓完必须做加总断言**：把 30 天报表的逐日值按周切片加总，与计划详情合计逐项比。
   **展现 / 点击 / 花费三项必然精确相等**（这两项与归因无关，是最稳的锚）；
   成交 / 购物车只有在同一归因下才相等；
3. **报告里只用一个口径，并把差异写进「诚实边界」**。混用 = 同一份数据两个结论。

> **跨后台交叉验证（最硬的一招）**：生意参谋首页「全站推广花费」（自然周）应与
> 万相台分日加总**完全一致**。实测 09-07~09-13：生意参谋 ¥2,532.28 = 万相台逐日加总 ¥2,532.28 ✅。
> **这一条通过，才说明两边登录态和窗口都没错位。**

**★ 二维判读法（规模 × 效率）—— 用下表演示**

> ⚠️ **下表是「示意数据」：数值经过虚构，只用来示范判读逻辑，不代表任何真实店铺。**

| 指标 | 本期 | 上期 | 环比 |
|---|---|---|---|
| 展现量 | 320,000 | 391,000 | **−18.16%** |
| 点击量 | 19,000 | 21,600 | −12.04% |
| 花费(元) | 13,800.00 | 13,100.00 | **+5.34%** |
| 平均点击花费(元) | 0.73 | 0.61 | **+19.67%** |
| 点击率 | 5.94% | 5.52% | **+7.61%** |
| 总成交金额(元) | 49,600.00 | 55,800.00 | −11.11% |
| 总成交笔数 | 960 | 1,150 | −16.52% |
| 总购物车数 | 2,850 | 2,849 | **+0.04%** |

> **只看到"成交跌 11%"是废结论。** 二维读法给出完全不同的动作：
> 展现 ↓18.2%、点击 ↓12.0%，**但花费 ↑5.3%、CPC ↑19.7%** → 不是"量掉了"，是"**买得更贵了**"；
> 点击率 ↑7.6%（素材/词没问题）+ 加购持平 +0.04%（承接没坏）
> → **归因指向流量供给端涨价**（大促前抢量 / 竞争加剧），不是自身运营问题
> → **动作 = 优化出价结构，而不是砍预算或改详情页**。

**判读要诀**：
1. **规模与效率必须分开看** —— 访客/展现是规模，转化率/点击率/CPC 是效率。只看金额会漏掉归因。
2. **CPC ↑ + 花费 ↑ + 展现 ↓ = 供给端涨价**（不是你的量掉了）。
3. **加购持平 = 承接没坏** —— 这是区分"流量问题"还是"商品问题"的关键先行指标。

> | 客户满意率 | 100.00% | 100.00% | 已触顶，无非改善空间 |

### ★ 售后服务页的隐藏结构：「退款维权分析」有 6 个子维度

默认只显示「退款原因」，但顶部可切换：


**「退款原因」表的字段**：

```text

```

**★ 由此固定的「退款归因三分法」**（v1.2 核心方法）：

| 类别 | 典型原因 | 含义 | 动作方向 |
|---|---|---|---|
| **主观冲动** | 不想要了 / 拍错·多拍·不喜欢 / 拍多了 / 买贵了·少用优惠 | **与商品质量无关** | **降冲动**（详情页预期管理 / 发货速度 / 催付话术） |
| **规格信息** | 订单信息拍错（规格·尺码·颜色）/ 尺码没选对 | 详情页规格表达不清 | **改 SKU 说明 / 加尺码引导** |
| **品质与物流** | 质量问题 / 做工粗糙有瑕疵 / 包装破损 / 快递一直未送到 | 真实的货与履约问题 | **改品控 / 换物流 / 补包装** |

**三条判读铁律**：

1. **先算结构占比，再看绝对率** —— 若「主观冲动」占成功退款金额的 **2/3 以上**，
   那么**"改品质"就是打错靶子**，正确方向是"**降冲动**"。
   **这条最容易搞反**：看到退款率高 → 本能去查质量 → 结论指向错误动作。
2. **「质量问题」要看 `完结退款率` 列的一个特例** —— 该列 **>100%** 表示
   **以前申请、本期才完结**，属**滞后兑现**，**不能当"本期质量突然变差"**。
   （同页的"尺码没选对""做工粗糙"也会出现 >100%，同理。）
3. **金额占比 > 笔数占比** 的原因类目 = **高单价品的退款** → 对 GMV 侵蚀更重，**处理优先级更高**。

> **✅ 正确读法**：日历空白 = **「现在还没到配置节点」**。
> 真正该算的是 **「上一场结束日 → 大促预售日」之间的空窗天数**：
> 中秋 09-27 结束 → 双11 预售 10 月中旬（去年 10-15）= **约 17 天空窗** ← 这才是可执行的风险点。
> 空窗期的考核指标要**换成先行指标**（加购率 / 加购增速 / 收藏），**不看成交、不看 ROI**（见 §4.5-②）。

**筛选器（直接决定"基准选谁"，很好用）**：

```text
活动类型  淘宝 / 天猫 / 聚划算 / 自定义
活动状态  所有 / 未开始 / 预热中 / 定金期 / 活动中 / 尾款期 / 已结束
活动时间  所有 / 最近30天 / 最近半年 / 最近1年
活动季节  所有 / 春季(3-5) / 夏季(6-8) / 秋季(9-11) / 冬季(12-2)
活动周期  全部 / 短(1天) / 中(<30天) / 长(>30天)
```

另有一键「**查看对比**」按钮 —— 平台自带的活动对比功能，优先用它，比手工算快。

### ② ★ 活动同期对比怎么做（重点条目）

> **报告生成时点若落在「活动进行中」或「活动刚结束（≤ 7 天）」→ 必须做活动对比，否则归因是错的。**
> 原因见 §4.5 三段结构：**大促期间/刚结束的"日常环比"天然失真**（蓄水期 ROI 掉、爆发期 ROI 虚高、回落期必然下滑）。

**选基准的优先级（务必按顺序找）**：

| 优先级 | 基准 | 怎么找 |
|---|---|---|
| 1 | **同类型近场活动** | `活动类型 + 活动周期 + 活动季节` 三维相同（如"天猫大促 × 中周期 × 秋季"） |
| 2 | **上一个同类活动** ⭐ | 活动列表按时间倒序，取最近一个同类（**最常用**） |
| 3 | **去年同期** | 活动时间筛「最近 1 年」+ 活动名含同一词根（两届同名活动） |
| 4 | **上月同期日常** | 无同类活动时退而求其次 —— 用**日常周**当基准，并**明确标注"非活动基准"** |

### ③ 🔴 铁律：活动之间「累计总量不可比，UV 价值可比」

活动时长不同（3 天 vs 20 天），**累计支付金额 / 累计引流访客数直接比毫无意义**。
活动列表把这两列一起给，正是为了让你算**第三个量**：

```text
UV 价值 = 累计支付金额 ÷ 累计引流访客数      ← 比值，剔除天数差异，跨活动可比
```

> ⚠️ **下表是「示意数据」：数值经过虚构，只用来示范算法与判读。**
>
> | 活动 | 活动期 | 累计支付金额 | 累计引流访客数 | 算出的 UV 价值 |
> |---|---|---|---|---|
> | 本场（进行中） | 12 天 | 48,000 | 8,000 | **6.00** |
> | 上一场同类（已结束） | 8 天 | 60,000 | 18,000 | **3.33** |
>
> **只比累计金额 → 会得出"本场不如上场（48,000 < 60,000）"的错结论。**
> **算 UV 价值 → 6.00 vs 3.33（+80%）** → **本场承接效率明显更好，只是活动期还没走完。**
> → **结论：活动期内的正确读法 = 看 UV 价值，不看累计总量。**

### ④ 已知限制（必须写进报告）

- **平台明文**：「因活动同步周期，**至少需 2 日**方可同步活动效果数据，建议提早完成报名和确认工作。」
  → **活动刚结束 0~2 天时，数据可能还没同步**；抓不到 ≠ 没发生，报告要标注「**数据同步中**」，
  **不许判"活动零效果"**。
- 活动列表**分页**（实测 10 页）→ 要找更早的基准需翻页。
- **「累计引流访客数」是"活动口径"**，与生意参谋首页的「访客数」定义不同 → **两者不可混用、不可相加**。

## 2.11 ★ 新品分析页 + UV 价值（v1.2 实跑打通）

**URL**：`https://sycm.taobao.com/cc/new_item_analysis`
**侧栏路径**：商品 → **新品追踪**（与「商品排行 / 商品360 / 品类360 / 商品集分析 / 重点商品」并列）

> **为什么必须单独看这页**：`cc/item_rank`（商品排行）**只覆盖访客数 Top500** ——
> **上新不久、量还没起来的新品根本排不进榜**，**新品多的店铺会整批漏掉**。

### ① 这页给什么

| 板块 | 内容 |
|---|---|
| 口径开关 | **日 / 7 天 / 30 天**（默认「日」→ **记得切**，见 §1） |
| 顶部条件 | **仅展示符合平台定义的新品**（另有「新品规则」「新品认定查询」自查入口） |
| **核心概况** | 新品数 / 访客数 / 加购人数 / 支付买家数 / 支付金额 —— 每项带**环比** + **同行同层平均** |
| **双线折线图** | **本店新品 vs 同行同层**（看自己爬坡 vs 行业爬坡） |
| **新品列表** | `序号 | 商品名称 | **新品类型** | 上新时间 | 访客数 | 加购人数 | 支付买家数 | 支付金额 | **UV 价值** | 操作` |

**「新品类型」的取值**：`小黑盒新品` / `普通新品` —— 小黑盒是平台给的**流量扶持位**，
**同批新品里谁进了小黑盒，就是平台给的优先级信号**。
（列表右侧还有「详情打爆分析」入口，但**属单品纵深 → 不在本日报做**，见「定位与边界」。）

### ② ★ UV 价值 = 平台推荐意愿的代理指标

```text
UV 价值 = 支付金额 ÷ 访客数
```

**它比"访客数"更能回答"平台愿不愿意继续给我这个品导流"**：

| UV 价值 | 平台会怎么做 | 我方动作 |
|---|---|---|
| **高于同行同层平均** | **继续给量 / 加量**（效率高，平台自己也赚） | 加预算、加库存、**别乱动价格** |
| **≈ 同行平均** | 维持分发 | 优化主图 / 详情页，把效率做上去 |
| **明显低于同行** | **撤量**（平台把流量给更高效的品） | **先诊断承接**（价格 / 主图 / 评价），**不要盲目加价买量** |

> **★ 与 §4.5 的「平台＝房东 / 广告商」一脉相承**：
> **UV 价值高 = 你在平台眼里是"高效率租户"** → 平台会主动给你更多免费推荐位。
> **这是新品期唯一值得盯的效率指标。**

### ③ 新品期的四条判读要诀

1. **新品期不看 ROI、不看成交金额** —— 量小、波动大（见 §4.5「蓄水期」读法）。
   改看 **UV 价值 + 加购人数环比**（先行指标）。
2. **同批新品之间横向比 UV 价值**，**不要纵向跟老品比** —— 老品有历史积累，UV 价值天然更高。
3. **两种病，两种药（最容易搞反）**：
   - **UV 价值高 + 访客极少** = 平台**还没发现你** → 动作是**「让它被看见」**（报小黑盒、开推广）；
   - **UV 价值低 + 访客很多** = 平台**给了量你没接住** → 动作是**改承接**。
4. **对照「本店新品 vs 同行同层」双线**：
   本店涨、同行没涨 = **你在抢量（真本事）**；两线同涨 = **大盘在涨（不是你的功劳）**。

## 2.12 ★★ 优惠券后台（v1.3 打通；**"突变必有因"里"自身变更"的第一数据源**）

**URL**：`https://qn.taobao.com/home.htm/coupon?isFirst=true&isNew=true&defaultTab=itemCouponList`

### ① 为什么这页必须进日报流程（2026-09-20 教训）

那一轮把"转化下滑 −47.80%"归因成 **"承接质量恶化"**（跳失率↑、人均浏览↓）→ 药方"改详情、加客服"。
**真实原因是优惠券力度从 9 折缩到 90.7~93.3 折（09-12 起），不再比同品牌专卖店便宜。药方完全开反。**
→ **券力度是"转化类异常"的最高频内生变量，却最容易漏查。**

### ② 怎么读（实测打通）

| 项 | 做法 |
|---|---|
| 规模 | 本店实测 **22 张券 / 3 页**（每页 10 项） |
| **翻页** | 点 **`button.next-pagination-item`** 且 `innerText === '2'/'3'` ⚠️ **不要用宽选择器点文本 "2"**（会点到消息角标 `span.notify_unreadNum__*`，实测踩过） |
| **取数** | **`document.body.innerText`** 即可 —— 表格是自定义 div 渲染，`table` 选择器抓不到 |
| 每张券记 | 券名 / **券ID** / 优惠详情 / 领取状态 / **领取时间** / **可用时间** |
| 逐行明细 | 每行有「**数据**」按钮（核销率/成交）与「**操作记录**」（变更审计） |

### ③ 三条判读要诀

1. **力度必须折算成折数才能横向比**：`满X减Y` → **等效折扣 = (X−Y) ÷ X**。
   实测例：满500减50 = 9 折；满500减40 = 92 折；满3000减280 = 90.67 折。
2. **⭐ 状态「已结束」但可用期还没到 = 被手动提前结束** —— 这是**改券时点的铁证**。
   实测例：`满100减10` 可用期写着 09-01~09-28，但 09-20 查已是「已结束」→ **推得改券在 09-12**。
3. **按同一门槛档做跨批次对比**，才能看出"哪个档位被削、削了多少"：
   | 门槛 | 8 月批 | 09-12 起 | 变化 |
   |---|---|---|---|
   | 满500 | 减50 = 9 折 | 减40 = 92 折 | **每单少减 10 元** |
   | 满1000 | 减100 = 9 折 | 减80 = 92 折 | 少减 20 元 |

### ④ 两个坑

- **领取量 ≠ 效果**：新批券领取量 537（9 天）> 老批 240（4 天），看着更好，
  其实只是**流量在涨**。**判断券的效果必须看核销率 / 成交，不是领取量。**
- **本页只列"店铺券"**（`defaultTab=itemCouponList`）；**"商品立减券"是另一个工具**，
  且平台公告该工具 **2026-09-28 起下线**（"不再支持新创建、复制和自动续期"）
  → **店主赶在工具下线前重做券体系，是力度被顺带调小的常见动机**，要留意。

> **★ 这页的价值不止在本店**：任何"转化突然变差"的诊断，
> **都应该先来这页确认"最近有没有改券"**，再去谈流量与承接。

## 4. 日报结构（15 段，照此组织）

> **段数沿革**：v1.0 = 9 段 → v1.1 = 12 段（+逐日趋势 / 区域时段 / 活动节奏）→ **v1.2 = 15 段**
> （+**新品与 UV 价值** / **服务健康** / **异常告警**）。
> 三次扩容针对三个缺口：**① 缺趋势**（只有快照，答不了"比上周好了还是差了"）、
> **② 缺基准**（活动期拿日常当尺子 → 必然误判）、
> **③ 缺预警**（数据都摆着，但没人"特别说明"）。
> **只有把异常顶到台面上、并给出台阶式判据，日报才有人看。**

0. **抬头 meta**（不是 h2，放在标题下）：生成时间 / 类目 / 店铺层级排名 / 体验分；**口径说明**单独一行。
1. **一句话结论**：5 条以内，先给最反直觉、最有价值的（如"流量涨 +20% 但转化崩 −28%"）。
   **命中「高危」告警时，结论第 1 条必须是它。**
2. **昨日核心指标**：6 格 KPI 卡片（含环比前一日）。
3. **上周 vs 上一周期**：指标表（含环比）+ 自洽反算 + 月度进度。
4. **★ 逐日趋势与拐点**（v1.1 新增）：近 14 / 30 天**逐日序列**（万相台报表「分天」直接取，见 §2.7）
   + 周环比 + **拐点标注**（哪一天开始转向）+ 一条趋势结论。
   **口径＝账户 / 渠道 / 计划级**（店铺维度）。
   **没有这段，日报就答不了"这周比上周好了还是差了"。**
5. **近 7 天流量**：指标表（含环比）。
6. **人群画像**：性别/年龄 + 城市 Top10（近 7 天日均），并给一句人群判断。
7. **★ 区域与时段**（v1.1 新增）：省份明细表（点击/花费/转化率/CPC）+ **四条地域判据**（漏水区 / 高潜区 /
   高成本区 / 样本不足）+ 时段分布。**必须附口径天花板声明**（地域不含全站推广、时段仅店铺级）。
8. **商品 Top10（排行榜即可，不做纵深）**：近 7 天表（支付金额/环比/退款）+
   **一句话结构判断**（集中度如何 / 头部是否下滑 / 谁跌出榜 / 有无黑马）。
   **边界**：这里是**店铺结构透视镜**，不是单品诊断台。发现异常品的正确写法是
   「→ 建议对 XX 品单独跑 `taobao-item-channel-diagnosis`」，**不在日报里展开它的渠道×词级拆解**。
9. **★ 新品与 UV 价值**（v1.2 新增；数据源见 §2.11）：
   ① 新品概览 5 数（新品数 / 访客 / 加购人数 / 支付买家数 / 支付金额，各带环比 + **同行同层平均**）；
   ② 新品列表（含 **新品类型**（小黑盒 / 普通）与 **UV 价值**）；
   ③ **一段"平台推荐意愿"判读**（UV 价值 vs 同行同层 → 加量 / 维持 / 撤量）。
   **为什么必须有**：商品排行**只覆盖访客 Top500**，新品排不进去就被**整批漏掉**；
   而**新品期唯一该盯的效率指标就是 UV 价值**。
10. **推广表现**：分场景花费/点击/ROI；点明"广告成交占 GMV 的比例"。
    **🔴 表格必须三行自洽**：`全站推广` / `关键词推广` / `店铺直达` / **合计**。
    万相台账户合计**包含「店铺直达」**（关键词报表页自述："以下数据仅含「关键词推广、店铺直达」"），
    **只列前两行会出现"两行相加 ≠ 合计"** —— 2026-09-20 某工业品店 实测差 **11.55 元 / 7 点击**。
    **验收标准：三行花费之和 == 合计花费，三行点击之和 == 合计点击**（点击同理，两列都要对）。
    某行为 0 或不可得时填 `—`，**不许删行**（删行即不自洽）。`店铺直达` 无成交时 ROI 填 `—`。
11. **★ 活动节奏定位 & 历史活动对比**（v1.1 建段 / v1.2 强化；数据源见 §2.10）：
    ① 本期落在哪个大促阶段的判定（§4.5 三段结构）；
    ② **若落在「活动进行中」或「活动刚结束 ≤7 天」→ 必须做跨活动对比**：
    选基准（**同类活动 → 上一个同类 → 去年同期 → 上月日常**）→ **比 UV 价值，不比累计总量**；
    ③ **写明用了哪个基准、为什么选它** —— **基准选错 = 系统性误杀**。
12. **★ 服务健康**（v1.2 新增；数据源见 §2.9）：**四块各给一句结论** ——
    **真实体验分**（分数 + 是否「规则不达标」）/
    **核心监控**（咨询率 · **平均响应时长** · 3 分钟人工响应率 · 满意率 · 客服排名，**逐项对「同行同层优秀」**）/
    **售后服务**（**成功退款率** + **退款原因三分法结构占比**）/
    **物流洞察**（时效与异常；**抓不到就写"未取到"并给替代来源**）。
13. **★ 异常告警**（v1.2 新增；分级规则见 §4.7）：**三列表（级别 / 指标 / 说明与建议）**，
    按 **🔴高危 → 🟡中危 → ⚪观察** 排序。
    **这一段是日报的"报警器"** —— 凡命中 §4.7 触发条件的，**必须在这里逐条特别说明**，
    **不许只在正文里带过**。
14. **变化点 & 可能原因**（三列表：变化点 / 数据 / 归因判断）。
15. **风险预警 & 建议动作 + 下阶段预判**（§4.6 的区间外推 / 拐点预警 / 归因清单并入此段）。
16. **★ 需人工确认清单（v1.3 新增，**"别自己瞎猜"的落地形式**）**：
    **凡归因无法用后台数据验证的，一律不得写成结论**，改为列成清单交运营/店主确认。
    **表格三列**：`待确认事项` / `为什么怀疑它` / `去问谁`。
    **候选因素从 §4.8 因素库里挑**（价格 / 尺码 / 库存 / 图片 / 优惠 / 差评 / 活动前期 …），
    **AI 能自查的先查完**（券后台 / 库存 / 评价 / 活动日历 / 归因口径），只把查不到的留给运营。
    **判定标准**：若日报里出现了"承接能力不足""流量质量下降"这类**现象名称**却**没给出验证路径**，
    **就是瞎猜，必须改写成本清单的一条**。

**★ 归因闸 v2（2026-09-20 新增，**顺序不能跳**）**：

| 闸 | 查什么 | 说明 |
|---|---|---|
| **闸零 · 自身变更** ⭐⭐ | **价格 / 优惠券力度 / SKU 断码·断色·断货 / 库存 / 满减 / 包邮门槛 / 主图 / 详情** | **最可控、最易核实、最易被遗忘**。券力度去 `qn.taobao.com` 券后台查实（见 §2.12）。**「断色」和「改券」同属自己方的人为事实**（某母婴店 先例：2 个单品转化下降 = 断色）|
| **闸一 · 竞店对标** ⭐ | 同品牌其他授权专卖店 / 同类竞品的**券后价**、赠品、运费 | 价格优势丧失 → 转化**立刻**掉，**加预算救不回来** |
| **闸二 · 口径成熟度** ⭐ | 万相台**归因未回补日**是否被算进分子分母；两窗口成熟度是否一致 | 见 §1「归因成熟度陷阱」|
| 闸三 · 日历 | 大促 / 节令 / 物流停运 | — |
| 闸四 · 节奏 | 蓄水期 / 回落期 | 见 §4.5 |
| 闸五 · 投放 | 流量 / 出价 / 创意 | **放最后**，别一上来就调价 |

> **⚠️ 闸零里为什么必须有「断码断色」**：**断色不在推广数据里、也不在跳失率里**，
> 但它会直接打掉单品转化。**某母婴店 真实先例：2 个单品转化率下降，最后查出来是断色。**
> 早先把供给单列在后面是错的 —— **它和"改券"是同一类（自己方的人为变更），必须在闸零一起过。**

**归因写法**（第 14 段是灵魂）—— **归因层级止于「店铺 / 渠道 / 计划」三档**，
单品层的问题只做"点名"，不做归因展开：
- 先看**降幅结构**：买家降幅 > 访客降幅 → 不只是流量少了，**转化也弱了**；只看总量会漏掉这层。
- 再看**投放动作**：推广花费是否被主动加码/砍掉。"加投放 + 转化下滑"= 用更贵的流量买更低的效率。
- 区分**结构变化**与**总量变化**：量跌但客单价升 = 结构向高价迁移（有利利润率）。
- 每个变化点都要有**"判断"**（走向/严重度），不能只描述现象。
- 报告尾部**必须**标注：数据来源与采集时间、各口径定义、颜色约定、"AI 问数"类演示数据未采用、**抓不到的写"未取到"**。
- **若为活动期：注明本期是"活动进行中/刚结束"，并声明所有环比已按 §2.10 做过活动基准校正。**

### 4.5 ★ 活动淡旺季节奏（v1.1 新增；归因必不可缺的上下文）

> **不先定位"这周落在哪个节奏里"，归因必然出错。**

实测万相台首页会直接播报返点活动进度（如「双11抢跑返点计划」）→ 反推**双11 返点活动 10 月初就开跑**。

**② 大促的三段结构（判读铁律）**

| 阶段 | 特征 | 怎么读 |
|---|---|---|
| **蓄水期**（大促前 2~4 周） | 加购 ↑、成交平、**ROI 掉** | **只看加购率 + 加购增速，绝不看 ROI**；ROI 掉了不是坏事 |
| **爆发期** | 成交暴涨、**ROI 虚高** | 自然成交会被算进付费功劳（**口径灌水**，别当真实效率提升） |
| **回落期** | 成交跌破日常 | **不能判"衰退"**，必须跟**去年同期**或**上一个非大促月**比 |

**两个反常识（提前防误判）**：
1. **大促前日常流量会掉** —— 平台把免费流量导向大促会场，日常访客 ↓ **不是你的问题**。
2. **大促后必然回落** —— 拿环比读会得出"暴跌"的假结论，**那只是需求被提前透支**。

**③ ★ 波动品识别：先打标签，再选基准**

> **用错基准 = 系统性误杀**（把旺季品当衰退品砍掉）。

| 波动类型 | 典型例子 | 波动来源 | **正确的基准** |
|---|---|---|---|
| **季节品** | 服装（春夏秋冬） | 季节更替 | **同比**（去年同月），**不是环比** |
| **事件 / 场景品** | 出行场景品（降噪类、旅行颈枕、晕车用品…） | **外部事件日历** | 绑定**春运 / 暑运 / 黄金周 / 开学季** |
| **大促驱动品** | 各类囤货品 | 平台大促 | 大促周期对齐（见 4.5-②④） |
| **稳定品** | 日用消耗品 | 自身运营 | 环比 + 滑动窗口（正常做法） |
| **新品** | 上架 < 90 天 | 冷启动爬坡 | **不与老品同基准**，只看自身斜率 |

**识别方法：看逐日曲线形状**（← 这就是 §4 第 ④ 段逐日趋势的另一个用途）

| 形状 | 判定 |
|---|---|
| 长周期平滑升降（跨月） | 季节品（与气温/季节同步） |
| 短促尖峰，峰值能对上具体日期 | 事件品 |
| 尖峰与平台大促日历同步 | 大促驱动品 |
| 围绕均值的窄幅波动 | 稳定品（可放心用环比） |

> **⚠️ 反例警示（必须写进结论）**：
> 拿**事件品的淡季**做环比 → 得出"该品衰退" → **砍掉一个旺季能爆的品**。
> 这类品在淡季（如春运结束、暑运未到）环比必然是负的 —— **这不叫衰退，这叫淡季**。
> **正确动作**：看它去年暑运/春运的峰值能不能复现，而不是看淡季斜率。

**④ 自建大促日历知识表（平台只给近 1~2 个月，这张表补"远期"的另一半）**

| 节点 | 大致时间 | 蓄水起点 | 备注 |

例：9 月中抓 7 天环比，落在"中秋 + 秋季上新"的蓄水/爆发交界 → **不能拿它当平常周**。

### 4.6 ★ 下阶段预判（v1.1 新增；AI 的增量价值，但必须限定形式）

**❌ 不做**：**点估计**（"下 7 天会卖 123 单"）—— 小店日数据量不够，黑箱预测必然失准。
**✅ 要做**：三件事。

**① 区间外推**
- 输入：近 3 个窗口的动量 + **活动日历修正**（4.5）
- 输出：**方向 + 幅度区间**（"维持当前动量，下 7 天访客落在 X~Y"）
- **绝不输出单一数字**

**② 拐点预警（最有价值）**

| 信号 | 观测组合 | 预判 |
|---|---|---|
| **蓄水信号** | 加购率 ↑ + 展现 ↑ 但成交平 | 未来 1~2 周成交要涨 → **提前备货 / 加预算** |
| **衰竭信号** | CPC ↑ + 转化率 ↓ | ROI 要掉 → 查出价结构 |
| **透支信号** | 大促后加购率骤降 + 访客正常 | 需求被提前消耗 → **别慌，别砍** |
| **天花板信号** | 推荐访客退潮 + 渠道倍数收窄 | 灌量结束，回到真实基本盘 |

**③ 归因清单**（不是预测，是"后面该盯什么"）
列出未来 30 天该盯的 **3 个指标 + 触发阈值 + 触发后动作**。

**★ 诚实边界（必须写进交付物，不许省）**：
- **只做方向，不做精度** —— 不说"会涨 12%"，只说"方向向上，量级 10~30%"
- **有活动/节日时误差显著放大** → 必须标注"**未含活动修正**"或"含活动修正"
- **AI 预测是参考，不是依据**

### 4.7 ★ 异常告警分级（v1.2 新增；要求"明显下降 / 低于阈值 / 倍数级变化必须特别说明"）

> **日报最容易犯的错不是"算错"，是"算对了但没人注意到"。**
> 把异常平铺在正文里 = **没有告警**。**必须单独成段、分级、带阈值与动作。**

**触发条件（命中任一条即入告警段）**：

| 类型 | 判据 | 例（示意） |
|---|---|---|
| **A. 倍数级恶化** | 环比恶化 **≥ 50%**（金额/流量类）或 **≥ 100%**（比率/时长效类） | 响应时长 +150% |
| **B. 突破优秀线** | 差指标 `本店 ÷ 同行同层优秀 ≥ 1.5`；或好指标 `优秀 ÷ 本店 ≥ 1.5` | 成功退款率 > 优秀 1.5 倍 |
| **C. 断崖** | 环比 **≥ 3 倍** 或 **≤ 1/3**（**无论方向都先查**是不是口径变/批量单） | 访客 −70% |
| **D. 平台自标异常** | 页面出现「**请关注**」/ 红色告警 / 「规则不达标」 | 体验分规则不达标 |
| **E. 结构性转差** | 占比结构突变（主观退款占比跃升、推荐流量占比骤变、单点依赖加剧） | 退款原因结构迁移 |

**三级定级**：

| 级别 | 定级条件 | 报告里怎么写 |
|---|---|---|
| 🔴 **高危** | 环比恶化 ≥ 50% ／ 突破优秀线 ≥ 1.5 倍 ／ 命中 D ／ 有明确资金或流量损失 | **进「一句话结论」Top1** + 独立条目 + **给当日动作** |
| 🟡 **中危** | 环比恶化 20%~50% ／ 结构性转差 ／ 命中 E | 独立条目 + **观察窗口**（下次什么时候再看） |
| ⚪ **观察** | 环比恶化 < 20% ／ **样本不足**（点击 < 20 ／ 访客 < 50 ／ 展现 < 200） | 一句话 + **标明样本量**，**不下结论** |

**三条写法铁律**：

1. **"特别说明" = 说清三件事**：
   **现象**（哪个指标、多少）→ **量级**（对谁比、几倍 / 几个百分点）→ **动作**（今天做什么）。
   **只写现象 = 没说明。**
2. **必须自带基准** —— 说"降了 50%"没有意义，要说
   "**环比前一周降 50%**"或"**低于同行同层优秀 1.8 倍**"。
3. **方向必须标注清楚**（跳失率 / 退款率 / 响应时长 **↑ = 变差**），否则读者会看反。

> **⚠️ 反向案例警示（写"高危"之前必须先过这一关，否则会误杀）**：
> **有些"恶化"是健康的**：
> ① **灌量退潮** —— 平台给的泛流量撤了（访客大幅下降），**但转化率反而大涨** → 这是**回到真实基本盘**，不是衰退；
> ② **蓄水期 ROI 掉** —— 大促前 ROI 掉是**正常**，该看加购（见 §4.5）；
> ③ **退款率升伴随客单价升** —— 高单价品退款率天然更高，**不是品质崩了**；
> ④ **金额退款率升但笔数退款率降** —— 是单笔金额结构变了，**不是退款变多**。
> → **凡要标"高危"，先自问一句："这会不会其实是好事？"**

### 4.8 🔴🔴 转化异常因素库（**可积累，每次复看必用**）

> **实战经验（2026-09-20）**：
> **「所以，你最多列出可能的因素，价格、尺码、库存、图片、优惠、差评、活动前期等等因素，
> 提出来让他去看，你只是AI，还没有碰到那么多问题，需要去积累」**

**这是 AI 在"归因"这件事上的职责上限：不要给原因，要给「候选因素清单 + 去哪查 + 谁来确认」。**

### ① 因素库（种子 7 类 + 已有实测）

| # | 因素 | 数据形状（转化异常时看什么） | 去哪查 / 怎么查 | **AI 能否自查** | 确认人 |
|---|---|---|---|---|---|
| 1 | **价格** | 转化↓但访客/加购正常；进店即离 | 自己后台价、**竞店/同品牌专卖店券后价** | ❌ 竞店价需人看 | 运营 |
| 2 | **优惠（券/满减/活动价）** | 转化台阶式↓；**券出现无券空窗** | `qn.taobao.com` 券后台（**按可用时间排一遍看断档**，见 §2.12） | ✅ **能自查** | AI 先查 → 运营确认 |
| 3 | **尺码 / 规格（断码断色）** | **单品**转化↓但推广花费正常；访客正常 | 商品发布/库存的 **SKU 状态**、商品 360 | ⚠️ 部分可查 | 运营 |
| 4 | **库存（断货）** | 转化↓且在售中；流量还在进 | 库存页 / 商品 360 | ✅ 能查 | AI 先查 → 运营确认 |
| 5 | **图片（主图/详情改过）** | 转化↓伴随**点击率也↓**（主图改了影响点击） | 商品发布的历史版本 / 素材中心 | ❌ | 运营 |
| 6 | **差评 / 评价 / DSR** | 转化缓降、客单可能同时降；**退款原因出现品质类** | 评价管理、体验分、退款原因结构 | ✅ 能查 | AI 先查 → 运营确认 |
| 7 | **活动前期（蓄水期）** | **转化↓但加购/收藏↑**；全店同降 | 活动日历（`myseller.taobao.com/.../seller/homepage.htm`） | ✅ 能查 | AI 先查 |
| 8 | **自家运营人为失误** | 无券空窗 / 活动结束未重启券 / 忘改回价格 | 券后台、活动报名页、操作记录 | ⚠️ 部分可查 | **运营** |
| 9 | **归因未回补（口径）** | 成交显示 0.00 的日子被算进分母 | 万相台逐日表 | ✅ 能查 | AI 自查 |
| 10 | **竞店动作** | 转化↓ + 竞店同款降价/上新/报活动 | 竞店页面、店透视 | ❌ | 运营去看 |

### ② 使用规则（三条）

1. **发现转化异常 → 不要写原因，写这份清单的"本次版本"**：
   从因素库里**挑出与本次数据形状相符的 3~6 条**，每条写
   **「现象特征 / 去哪查 / 请谁确认」**，直接交付运营。
2. **AI 能自查的先查掉，不把能查的也推给运营**：
   上表标 ✅ 的（券、库存、评价、活动日历、归因口径）**AI 必须先查完再交清单**，
   只把查不到的（价格对比、图片改动、断色、竞店）留给运营。
3. **⭐ 因素库是可积累资产**：每次排查中**发现的新因素**（尤其是"上次没想到、这次才撞上"的），
   **必须当场追加到上表**。**这张表的长度就是本技能的成长记录。**
   > 已知来源：价格/尺码/库存/图片/优惠/差评/活动前期（2026-09-20 种子）
   > ＋ 断色（某母婴店 先例）＋ 无券空窗·漏续期（某工业品店 实测）

### ③ 一句话记住

> **AI 的产出 = 「变动发现」+「候选因素清单」+「指向确认人」。
>  运营的产出 = 「事实确认」+「执行动作」。
>  在报告里写"承接能力不足""流量质量下降"这类现象名称 = 越界 + 瞎猜，必须改成清单条目。**

### 4.9 ★★ 店铺级「数据形状 → 引导」对照表（**总纲 ⓪ 的落地工具**）

> **怎么用**：日报里每发现一条变化，**先在这张表里找有没有对应行** →
> 有，就直接照它写引导（问句形态）；没有，**当场追加一行**。
> **这张表的长度，就是本技能的成长记录。**

| 数据形状（日报里会看到的） | 引导运营去查 / 去问 | 备注 |
|---|---|---|
| **全店访客↑ 但转化↓** | ① 上周价格 / 券动过吗？② **流量结构变了吗**（推荐占比是否突增）？ | ⚠️ **双解**：比价失败 or 平台灌泛量，**两句都要问** |
| **展现↑ 点击↑ 转化↓ 且 CPC↓** | 不是买贵了、是**买偏了** → 查全站推广匹配是否放宽、人群是否跑偏 | 看推广流量的词/人群构成 |
| **全店访客↑ 但浏览量↓ / 人均浏览↓** | 进来的是泛量还是精准量？看二级来源结构 | 与"灌量退潮"方向相反 |
| **推广花费↑ 成交↓（ROI 崩）** | ① **券到期没续？**（AI 先自查）② 全站推广匹配放宽？③ 竞店降价？ | **顺序不能反**，先查券 |
| **加购↑ 但成交↓** | 兑现率下降 → 查券力度、比价、凑单 | **加购是先行指标，成交是滞后** |
| **付款率 / 支付转化率 ↓ 但访客正常** | 结算环节出问题？包邮门槛 / 运费模板 / 库存不足 | 前台下单试一遍 |
| **付费占比↑ 自然占比↓** | **买到的是增量，还是从自己自然流量迁移的？** | 看投放前后自然流量总量 |
| **某渠道流量暴涨但转化极低** | 平台在**平衡它自己**（推荐灌量），**不是故障** | 别跟平台商业模型对抗 |
| **某地域 / 时段数据归零** | 物流停运？该地区断货？区域限售？ | 工业品看物流时效 |
| **退款率↑** | 查**退款归因结构**（主观冲动 / 规格信息 / 品质物流）→ 三分法各对应不同药方 | 见 §2.9 |
| **金额退款率↑ 但笔数退款率↓** | 单笔金额结构变了，**不是退款变多** | 别误判 |
| **客服响应时长↑ / 满意率↓** | **是否单点依赖**（只有 1 个账号在实际接待）？ | 查客服排班与账号 |
| **跳失率↑ + 人均浏览↓** | ⚠️ **形状双解**：① 竞店券后价反超了吗？② 主图/详情改过吗？ | **两句都要问**（某工业品店 实测教训） |
| **券出现无券空窗 / 只有最低档券** | 漏续期？活动结束忘重启？ | **漏续期指纹**，见总纲 ⑤ |
| **大促前日常流量↓** | **正常** —— 平台把免费流量导向会场，**不是你的问题** | 不许当"衰退" |
| **大促后必然回落** | **正常** —— 需求被提前透支，**环比会得出假"暴跌"** | 须用**同比**判 |
| **蓄水期 ROI 走低** | **正常** —— 此时看**加购率 + 加购增速**，**绝不看 ROI** | 见 §4.5 |
| **成交显示 0.00（近 1~3 天）** | **不是事故** —— 归因未回补，剔出分子分母再算 | 见 §1 归因成熟度陷阱 |

**三条使用规则**：

1. **一条变化配一条引导，问句形态。** 不许只列数字，也不许写成断言。
2. **AI 能自查的先查完**（券后台、活动日历、退款原因、归因口径、库存 SKU），
   **只把查不到的留给运营**（竞店、改图、断色、线下沟通）。
3. **新形状当场追加** —— 尤其是"这次没想到、撞上了才发现"的那类。

## 5. 坑清单（实测踩到的）

| 坑 | 现象 | 处置 |
|---|---|---|
| **裸 `bash script.sh` 失败** | `bin\bash.exe: line 3: bash: command not found`，exit 127 | 用 `/usr/bin/bash` 绝对路径，或让 `PortableGit/.../usr/bin` 在 PATH 最前（bin 里的 bash.exe 只是 shim） |
| **环比方向丢失** | 文本只有 `5.53%`，看不出是 + 还是 − | 必须读 `.cyclecrc` 的 class（`up`/`down`），走第 2.5 节结构化 JS |
| **误把同比当环比** | 卡片上两个百分比，「较去年同期」是 `syncCrc` | 用 `cyclecrc` 才是环比；同比仅供补充 |
| **首页默认不是「日」** | 默认落在「实时」，拿到的是今日实时 + 昨日全天基准 | 要昨日全天完整指标就点「日」 |
| daemon 被沙箱回收 | 每条命令都在 autostart 新 daemon，偶尔卡死 / `session not registered` | **run_in_background 常驻 daemon**，之后只连不启 |
| session 跨命令失效 | 下一条命令报 `session not registered` | 把 `start→navigate→probe→stop` 全放进**同一条命令**（脚本已内置） |
| stdout 丢失 | 命令 exit 0 但输出全空 | **一律落盘再 Read** |
| bash PATH 损坏 | `dirname`/`head`/`cat` not found | 命令开头重置 PATH（脚本已内置） |
| 异步加载 | 抓到"正在努力加载…"空表 | 等 10~15 秒；切口径后再等 15~20 秒 |
| 销售分析页卡死 | 只出 Redux 日志 | 改用**首页切「周」** |
| 猜 URL | 404 | 用本技能表 + `sycm-backend-data-mining` 的路由表 |
| **点「月」落到上月** | `RANGE=2026-08-01 ~ 2026-08-31`，误当 9 月进度 | 先读 `RANGE=`；如实写"8 月整月"；本月进度改从「店铺概况」取 |
| **月窗口不可外推** | 同一时期的"整月 GMV"与"滚动月窗口进度"数值可差一倍以上 | 两种窗口定义不同（整月 vs 滚动月），**不可换算** |
| **`tab borrow` 恒超时** | 用户标签被之前的 `nav` 搞脏后，`tab borrow <ID>` 每次都 `tool RPC timed out after 30s`，session 里始终只有 agent 空白页 | **改用 `tab create --session <SID> --url <目标URL>`**（见 5.6 节），完全绕开用户标签，且不要对用户标签做 `nav` |
| **`navigate` 跳不出 chrome://** | `tab create`（默认 `chrome://newtab/`）后 `navigate` 报 `Cannot access a chrome:// URL` | 别两步走 —— **`tab create` 时直接带 `--url`**，一步落在目标页 |
| **首页「周」不滚动** | 周五/周六读「周」，`RANGE` 仍是上周日~上周六（如 09-07~09-13） | 生意参谋的「周」要等本周走完才滚动。**本周经营数据改用「流量看板 → 7天」的滚动窗口**，并在报告里写明两个口径的差异 |
| **万相台 hash 路由不能省**（v1.1） | 只写 `#!/report/area` 少带 `?rptType=area` 会落到兜底页 | **整条照抄 §2.7 路由表** |
| **`region` ≠ `area`**（v1.1） | `#!/report/region?rptType=region` 报"页面不存在或无权访问" | 正确是 **`area`**；报错文案会误导成"权限问题" |
| **报表顶部"数据汇总"是账户级**（v1.1） | 进了「商品报表」以为看到单品，其实顶部那块是**全账户** | **明细表才是对应维度**；先确认维度标签再读数 |
| **地域报表口径窄**（v1.1） | 页面自述"**不包含货品全站推广、超播券…**" | 地域结论**只代表关键词等场景**，别当全店地域分布 |
| **访客分析的「下载」按钮无效**（v1.1） | 点击无报错，Downloads 无新文件（bsk 0.3.0 下仍如此） | **别在下载上耗时间**，老老实实走 DOM 抓取 |
| **万相台报表首屏 RPC 超时**（v1.1） | navigate 后 `tool RPC timed out after 60s`，但页面实际已渲染 | **重试一次即可**，不是失败 |
| **拿 7 天总量去比 30 天总量**（v1.1） | 两个窗口重叠，方向可能完全假 | 见 §1「7 天 vs 30 天不是趋势对比」；总量先**日均化** |
| **动态加载控件点击后不刷新**（v1.1） | 切粒度/翻页后立刻取值，拿到上一状态 | 每次切口径后 `sleep 8~12` 再读；用页面上的**日期区间文本**核对当前落在哪一段 |

## 5.6 🔴 最稳接入路径：`tab create --url`（2026-09-18 实战定型，优先用这条）

**背景**：`tab borrow` 借用户已开的标签看似方便，但一旦对该标签做过 `nav`，它的 CDP 会话会**死锁**，
此后 `borrow` 恒超时（30s），且 agent 空白页又跳不出 `chrome://`，整条链路卡死。

**解法：完全不用用户标签，每次 `tab create` 直接带 `--url`。** 登录态照样复用（同一浏览器 profile），
还不会打扰用户正在看的页面。

```bash
export PATH="/usr/bin:/bin:/mingw64/bin:/c/Windows/System32:/c/Windows:$PATH"
export BSK_HOME="${USERPROFILE}\.bsk"          # 例：C:\Users\<你>\.bsk
export BSK_AUTO_START=0
export BSK_UPDATE_MANIFEST_URL='https://127.0.0.1:1/version.json'   # 掐掉 30 分钟自杀
BSK="$HOME/.local/bin/bsk.exe"
nohup "$BSK" daemon start --foreground --daemon-idle 8h > /tmp/bsk.log 2>&1 &
sleep 8
SID=$("$BSK" session start 2>&1 | tail -1)
# ↓ 一步到位：新建标签直接落在目标页（不要 create 完再 navigate）
OUT=$("$BSK" tab create --session "$SID" --url "https://sycm.taobao.com/portal/home.htm" 2>&1)
TAB=$(echo "$OUT" | grep -o 'tab_id=[0-9]*' | head -1 | cut -d= -f2)
sleep 22            # 等页面异步加载
# ↓ 改口径：用 evaluate 找叶子节点 click，比 bsk click --text 稳
"$BSK" evaluate --session "$SID" '(function(){var els=document.querySelectorAll("span,div,a,button,li");for(var i=0;i<els.length;i++){var e=els[i];if((e.textContent||"").trim()==="周"&&e.children.length===0){e.click();return "CLICKED";}}return "NF";})()' --tab-id "$TAB"
sleep 18
# ↓ 取数必须带 --tab-id，否则打到 agent 默认标签
"$BSK" evaluate --session "$SID" '<取数JS>' --tab-id "$TAB" > /tmp/out.txt 2>&1
```

**关键参数细节**（踩过的）：
- `tab borrow --session <SID> <TAB_ID>` —— TAB_ID 是**位置参数**，不能写 `--tab`。
- `evaluate --session <SID> '<EXPR>'` —— 表达式是**位置参数**，不能写 `--expression`。
- `navigate --session <SID> [URL]` —— URL 位置参数。
- 多标签并存时，**所有读取命令都要 `--tab-id`**，否则默认打到 Agent Window 的活动标签（常是空白页）。

**一条命令打一个页面**：daemon `start` + `session start` + `tab create --url` + 点击 + `evaluate` 全部写在同一条 shell 命令里。
跨命令复用 SID 会 `session not registered`（每条 bash 各起一个 daemon）。

## 5.7 「对比上一次的数据」怎么做（2026-09-18 首次实践，很常用）

常见追加要求「**对比上一次的数据**」——指的是拿**本期日报**对上**上一期日报**（可能生成在**另一个工作区**）。

### 第一步：找到上次日报
同类日报可能落在别的 workspace。路径规律：`<用户目录>\WorkBuddy\<日期-时间戳>\运营日报\<店铺名>_运营日报_YYYYMMDD.html`。
```bash
ls -la "$HOME/WorkBuddy/<日期-时间戳>/运营日报/"
```
**上次的原始抓取数据通常也在那个工作区根目录**（`sycm_home.txt` / `sycm_home_week.txt` / `sycm_flow7.txt` / `sycm_item7.txt`）——
**直接读原始 txt 比解析 HTML 更可靠**（HTML 里的数字被标签切碎，`grep` 数字会碎成单字符）。用 `sed -n '27,200p'` 按行段读。

### 第二步（关键）：先做「同窗口交叉验证」，再谈对比
两次抓取若覆盖**同一个完整自然周**（如都含 `2026-09-07 ~ 09-13`），就把这一周的指标**逐项对撞**：
- 一致项越多 → 数据越可信（实测：十几项指标中绝大多数能完全对上）。
- **差异若全部落在退款类指标**（净支付 / 金额退款率 / 订单退款率）→ 判定为**归因窗口回填**（退款按「完结时间」口径会持续补录），**不是抓错数**，报告里要写清楚，别改数也别慌。
- 差异若落在**非退款类** → 那才是真问题，要查。

### 第三步：三组对比表
| 组 | 对什么 | 注意 |
|---|---|---|
| 昨日 vs 上次昨日 | 单日 KPI + 推广 ROI | **不同自然日不可当趋势线**，只做"环比脉冲"参考，报告里要标注这一限制 |
| 近 7 天 vs 上次近 7 天 | 流量/人群 | 窗口重叠 5~6 天，做**趋势参考**，不当精确对比 |
| 上一期商品榜 vs 本期商品榜 | 单品 GMV/访客 | 列出榜位进出变化（谁跌出 Top10、谁补入） |

### 第四步：把「系统诊断文案」也拉成对照表
首页「智能诊断 / 投放建议」区块的**文字会随周期变**，两次抓取对比能看出平台的判断方向。本次实测出两条很硬的信号：
- 自然 IPV：从「小幅下滑、明显落后同行」变成「**大幅下滑**、落后收窄」（**退坡加深**）
- 自然搜索 CTR：从「**领先**同行」变成「**落后同行** 且环比下滑」（**由领先翻转**）
这类"平台自己说的话变了"是**独立于我方指标的第二证据源**，用来印证结论特别有力。

### 第五步：明确写出「两口径方向相反」时的读法
实测出现过：**昨日 GMV 翻倍，但近 7 天访客同比为负**。
正确读法是：单日高产出建立在**退坡的流量底板**上 → 要追问"转化率回落后撑不撑得住"，**不能拿单日翻倍当新基线**。
这是日报里最容易被忽略、也最容易被上级误读的地方，**必须写进一句话结论**。
| 「AI 问数」假数据 | 数字整齐递增 | 禁用，不当数据源 |
| 脚本 CRLF | `bash: $'\r': command not found` | `sed -i 's/\r$//' script.sh`（脚本内已自处理） |
| **服务页环比无正负号**（v1.2） | 「较前 1 日」后面挂的是裸数字（如 `150.00%`），方向同样丢失 —— 与首页 `cyclecrc` 同源 | **别用 innerText 猜方向**；用旁边的**「同行同层优秀」基数反推**，或结构化读 class |
| **真实体验分 / 物流洞察抓不到**（v1.2） | 单抓 `/qos/service/...` 外层 URL **返回空** —— 它们是**侧栏折叠菜单的 JS 路由** | **先点父级「考核」/「物流」展开，再点子项**；仍拿不到就**降级 + 写"未取到"**（§2.9） |
| **活动效果数据有 ≥2 天同步延迟**（v1.2） | 活动刚结束当天抓，列表里该活动的累计金额/访客**可能为空或 0** | 平台明文规定；**标注"数据同步中"，别判"活动零效果"** |
| **拿累计金额跨活动比**（v1.2） | 3 天活动 vs 20 天活动比累计 GMV → **必然误判** | **算 UV 价值（金额 ÷ 引流访客）**，比值才可比（§2.10） |
| **新品整批漏掉**（v1.2） | 只抓 `cc/item_rank` → **它只覆盖访客 Top500**，新品排不进榜 | 另抓 `cc/new_item_analysis`（§2.11） |
| **把新品跟老品比 UV 价值**（v1.2） | 老品有历史积累，UV 价值天然更高 → 新品被判"不行" | **同批新品横向比**；新品看**自身斜率**（§4.5 波动品识别） |

## 6. 可选：挂成每日定时任务

若要"每天早上一键出日报"，用 automation 工具建**每日定时**任务（而非本技能内硬编码时间）。
提示词要自包含：说明店铺名、目标后台（生意参谋）、要抓的页面、口径要求（昨日 + 上周对比 + 近7天 + 月度进度）、
输出路径与命名、以及"数据必须实抓、禁止估算"。
注意：**依赖本机开机 + Chrome 已登录**，做不到 7×24 无人值守。

## 7. 红线

- 🚫 **不要把真实店铺数据写回本技能文件。** 本技能是**公开技能**：
  里面的任何示例都必须是**示意值**（虚构数字 + 通用代称，如「A 省 / 示例店」），
  **绝不能把某个真实店铺的 GMV、转化率、省份明细、活动报名情况抄进来当"实战样例"**。
  真实数据只应留在**用户自己的工作区**（报告 HTML 与原始抓取 txt）。
  同理：**本机绝对路径（含用户名）也不要写进技能文件**，一律用 `$HOME` / `${USERPROFILE}` / `<占位>`。

- 🚫 **不越界做单品纵深。** 本技能是**店铺维度**：出报告时若出现「词级明细表 / 单元级拆解 /
  单品搜索vs推荐结构 / 废词判定」，**说明已经跑偏**（见「定位与边界」）。
  单品问题在日报里**只点名、不展开**，展开请转 `taobao-item-channel-diagnosis`。

- 🚫 **服务 / 活动 / 新品页的示例也必须是示意值。** §2.9 / §2.10 / §2.11 与 §4.7 里的
  响应时长、退款率、成功退款金额、活动累计 GMV、UV 价值、客服账号名……**全部只能用虚构数字 +
  通用代称（「示例店」「A 客服」）**。活动名若要用，**只用平台公开的大促名**（如"超级 88""618"），
  **不要写某店的报名状态与活动效果数据**。

- **只读**：不点任何"导出/下载/提交/改价/改预算"等写操作；要动写操作先向用户确认。
- 不读 cookie / token / 密码。
- 不把"看起来很整"的数字当数据。
- 报告里每个结论都要能指回某个具体数字。
